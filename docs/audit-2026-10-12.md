# Audit: security, correctness and workflow

Date: 2026-10-12. Baselines: main `9770854d4e81b61da810c083fd588430086c6f46` and active Windows branch `72fe44a455cb375ce4d8cf5e7cf0ed957a27ab90`.

## Scope and decision

Audit the CLI capture/export modules, Windows launcher and worker boundary, dependency specifications, synthetic tests and GitHub Actions. Main contains the CLI; the Windows application is developed separately in `feat/windows-desktop`. Apply core safety fixes and CI to main, then propagate them and desktop-specific fixes to the Windows development branch. Publishing the entire desktop feature to main is a separate integration decision.

All regression inputs are synthetic. No taxpayer records, saved profiles, live credentials or real Coretax sessions are used. Local Linux verification cannot establish Windows Edge, Credential Manager, Job Object or frozen GUI behavior; the PR's Windows checks are the merge gate for those boundaries.

## Confirmed findings and remediation

| Priority | Finding | Remediation |
| --- | --- | --- |
| P1 | A resumed detail-limit run can merge later checkpoints by record ID without checking taxpayer/year scope; checkpoint dictionaries can overwrite inventory provenance. | Validate the same scope and inventory identity at both read points. Merge only validated capture fields. Revalidate export record scope/year. |
| P1 | API responses and checkpoint navigation do not consistently enforce the exact HTTPS origin; detail URLs establish taxpayer but not return identity. | Validate origins before navigation or identifier fill, explicitly validate API success/schema, and match taxpayer plus return ID for a detail capture. |
| P1 | Long cells are silently truncated, certain numeric values are rounded or blanked, and invalid XML characters can break the workbook. | Validate source and derived cell values before saving; reject unrepresentable cells without changing raw data; preserve page-context chunking. |
| P1 | Workbook files are overwritten before all validation completes; orphan workbooks or case variants may be replaced without verified scope. | Stage and verify the full set, enforce scope/file-set guards, retain previous files if verification fails, and roll back completed replacements if a later replacement fails. |
| P1 | Runtime output checks are Python assertions and disappear under `python -O`. | Use explicit runtime exceptions and test verification in an optimized child interpreter. |
| P1 | uv 0.12.16 is vulnerable to Windows wheel-extraction path traversal, affecting the desktop installer/build tool. | Pin uv 0.12.18 across CI, desktop runtime and build requirements; require at least this version in the CLI setup script. |
| P2 | Truthy completion flags, capture errors or incomplete tables can still produce a misleading COMPLETE label. | Require boolean completion flags and consistency between run errors, records and table completion. |
| P2 | Arbitrary file, UNC or application URLs become clickable spreadsheet links. | Keep the original text but activate only HTTP/HTTPS links. Formula-looking strings remain literal text. |
| P2 | Observer retains all response batches, and failed View popups can remain open. | Keep one latest response plus a monotonic sequence; track the initiating page's popup and close invalid popups. |
| P2 | Inventory deduplication ignores conflicting submission-date metadata. | Reject conflicting submission dates instead of silently selecting one. |
| P2 | Main has no test workflow; Windows builds run only on pushes and have no dependency cache or vulnerability gate. | One Windows job checks PRs and pushes, caches uv packages, audits actual installed dependencies, tests once, then builds and verifies desktop artifacts when available. |

The upstream uv advisory is [GHSA-2cv4-cqwr-gwf7 / CVE-2026-104843](https://github.com/astral-sh/uv/security/advisories/GHSA-2cv4-cqwr-gwf7). It affects Windows uv versions from 0.12.7 up to, excluding, 0.12.18. The patch is [uv 0.12.18](https://github.com/astral-sh/uv/releases/tag/0.12.18). This audit found the vulnerable dependency, not evidence that the application was exploited.

## Verification method

Start with the existing suite and distinguish environment failures from application defects. Add regressions that fail on the baseline, then verify source values, scope, output bytes after failed publication, completion flags and browser/protocol boundaries. Test optimized Python in a child process so assertion removal is exercised. The Windows workflow runs the full synthetic suite and audits the installed dependency set; the desktop path additionally builds and exercises the frozen GUI.

Audit application requirements separately from the agent's tooling environment. The initial six resolved production packages had no known advisories. The initial build dependency scan found uv 0.12.16. Old pip installed by the local environment is not an application requirement; the CI worker environment is created by uv without pip and the audit tool runs separately.

CI uses full commit-SHA action pins, a read-only repository token and no persisted checkout credentials. Only trusted push/manual/scheduled runs save the package cache. Profiles, checkpoint JSON and generated taxpayer workbooks are never cached or uploaded. These choices follow the [GitHub secure-use guidance](https://docs.github.com/en/actions/reference/security/secure-use) and [uv setup action configuration](https://github.com/astral-sh/setup-uv).

## Remaining recommendations and boundaries

1. Enable a repository ruleset requiring the **Windows tests and dependency audit** check and reviewed pull requests for both maintained branches. Main is currently unprotected and the repository has no rulesets. A green check alone does not prevent later direct pushes.
2. Sign distributed Windows executables with a maintainer-controlled signing identity. The checksum manifest establishes content integrity against the build artifact; it does not replace publisher authentication. Keep signing secrets out of pull-request runs.
3. Use an authorized live acceptance run after deployment to confirm current intranet selectors and an Excel UI spot check. Synthetic fixtures establish application behavior, not that a changing remote portal still has the same layout.
4. Consider a fully resolved, hashed dependency lock as a follow-up. Direct dependencies and tools are pinned and audited; transitive versions still resolve at installation. Introduce locking together with the worker resource fingerprint and installer validation, rather than silently changing their contract.
5. Preserve the existing limited capture scope. PDF/BPE contents, generated remote documents and row drill-down dialogs remain outside the supported scope. A COMPLETE workbook means the documented exposed-page scope was reconciled.
6. Recovery is designed for Python exceptions and ordinary file replacement failures. A process kill or power loss during a multi-file replacement is not a fully atomic transaction. Keep raw checkpoints and recover blocked exports into a new output folder.
7. Missing legacy per-record scope metadata cannot independently prove NPWP provenance. New captures/checkpoints carry scope, supplied scope is always checked, and current capture URLs must establish the selected taxpayer and return.

No numeric speedup or memory percentage is claimed without a matched benchmark. The concrete resource changes are bounded response retention, removal of redundant workbook rereads during verification, reuse of dependency downloads, cancellation of obsolete CI runs, and avoiding a second compression pass for an already compressed executable artifact.
